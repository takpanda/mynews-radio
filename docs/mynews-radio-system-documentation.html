システム概要

mynews-radio は、ニュース記事の収集から音声番組の配信までを行う「パーソナルニュースラジオ生成システム」です。LLMはフェーズ別にプロバイダーを選択でき、標準構成では要約にローカルLLM（通常はOllama）、台本生成・レビューにCodexを使用します。音声合成はFish S2 Proを既定とし、VOICEVOX / AivisSpeechはコード上で無効化されています。

主要な機能

  • 記事取得 — はてなブックマーク系API（news.beeworks.cc）、はてな ホットエントリRSS、Yahoo!ニュースRSS の3ソースから記事を収集し、SQLite に upsert
  • 要約生成 — 設定された要約LLM（既定はOllama）で各記事を日本語要約し、カテゴリ・重要度（1〜5）・難易度（1〜3）を付与
  • 台本生成 — Narrative Arc（番組全体の構成案）を先に生成した上で、男女2人のトーク形式のラジオ台本（JSON）を生成。トランジション自動挿入と自動Linterによる品質チェック・再生成を実施
  • 4ディレクターレビュー — 「天才」「初心者」「心配性」「ポジティブ」の4キャラクターによるLLMレビューを集約し、同じエピソードの台本を改訂（レビュー失敗時も通常は生成を継続）。レビュー後の最終検証で管理者確認が必要な状態に遷移する場合あり
  • 音声合成 — Fish S2 Proを既定エンジンとして行ごとにWAVを生成。読み置換テーブル適用、トランジションジングル/無音挿入、サンプリングレート正規化を実施。VOICEVOX / AivisSpeechは現行コードでは無効
  • エピソード組み立て — ffmpeg でWAVを結合し、オープニング/エンディングジングル（フェード付き）を付加して episode.mp3 と metadata.json を出力。各セリフに再生開始秒（start_time）を付与
  • 配信 — FastAPI が HTTP Range 対応で音声をストリーミング配信し、Next.js 製のWebフロントで再生・台本閲覧・手動生成が可能

全体アーキテクチャ

システムは Docker Compose 上の3サービス（api / web / proxy）と、設定されたLLM・TTSプロバイダーおよびニュースソースで構成されます。永続データはホストの ./data ディレクトリ（SQLite DB・エピソード成果物・ジングル・ログ）にボリュームマウントされます。

コンテナ構成（docker-compose.yml）

サービス役割ポート主な設定
apiFastAPI（REST API・音声配信）8010TZ=Asia/Tokyo、./backend:/app と ./data:/app/data をマウント。現行 compose は uvicorn を直接起動する
webNext.js フロントエンド（depends_on: api）内部3010./frontend:/app をマウント、node_modules は匿名ボリューム。npm run dev で起動し、ホストには直接公開しない
proxynginx 公開入口・ヘッダー処理ホスト3010 → proxy:80infra/nginx/public-entry.conf を使用。公開用トークン設定が必要

backend/entrypoint.sh は cron と uvicorn を起動するが、現行 docker-compose.yml は command で uvicorn を直接起動するため entrypoint を迂回し、cron は起動しない。日次バッチをComposeで動かす場合は起動設定の確認が必要。cron の時刻は TZ=Asia/Tokyo に従い、Compose の schedule 既定値は 30 16 * * *、.env.example は 0 21 * * *。

データモデル（ER図）

永続化は SQLite ファイル（既定 data/mynews-radio.db）で行います。中心となる記事・エピソード・構成項目のほか、生成ジョブ、管理者セッション、監査ログ、番組・MC、プロンプト、通知、辞書などのテーブルがあります。新規DBは app/db/schema.sql で作成し、既存DBには app/db/migration.py と起動時の追加マイグレーションを適用します。下図は中心となる3テーブルの簡略図で、全スキーマではありません。

ステータス遷移

テーブル列取りうる値意味
articlesstatusnew → summarized → used / error取得直後 → 要約済み → 台本に採用済み。本文不足やJSON解析失敗時は error
episodesstatuspending / waiting / generating / awaiting_review / synthesizing / completed / failed生成ジョブの待機・実行、管理者レビュー待ち、合成、完了・失敗を表す
episodesphasestart → import → summarize → generate_script → review → review_done → final_validation → synthesize → build → complete生成進捗表示用。API経由では詳細メッセージを含めてフロントへ返す

SQLite の database is locked 対策として、EpisodeService には指数バックオフ付きリトライが実装されています。生成要求は generation_jobs に永続化され、所有者・操作単位の冪等性キーとFIFOキューで重複・同時実行を制御します。エピソード日付の部分一意インデックスで二重実行を防ぐ設計ではありません。

86.0

手動生成フロー（Web → API）

Web フロントの「生成」ボタンはNext.js API Routeを経由して POST /generate を呼び出します。管理者セッションと一意な Idempotency-Key を検証した後、永続ジョブをFIFOキューに登録します。実行可能なジョブはバックグラウンドスレッドで処理し、同時実行中なら waiting として待機します。フロントは GET /episodes/{id} をポーリングして status / phase / generation_message を表示します。

services/ — 外部サービスクライアントとドメインサービス

モジュール責務
llm_provider.py / 各クライアント要約と台本・レビューのLLM選択を独立管理。Ollama / vLLM / LM Studio / Codex等を構成し、既定は要約がローカルLLM、台本・レビューがCodex。環境設定やリクエストでプロバイダー・モデルを上書き可能

article_service.py記事の upsert（URL一意で重複判定）、status=new の取得、要約結果の保存、台本用要約の取得（importance_score >= MIN_IMPORTANCE_SCORE でフィルタし上位 MAX_SCRIPT_ARTICLES 件）、使用済みマーク
episode_service.pyエピソードの CRUD・状態/フェーズ更新・期限切れ取得。SQLite ロック競合に対する指数バックオフ付きリトライを適用
generation_control.py生成ジョブの永続化、冪等性キー検証、FIFOキュー、同時実行制御と完了処理
ffmpeg_service.pyffmpeg ラッパー。WAV結合（concat）、WAV→MP3、任意音源→WAV正規化（24000Hz/mono/s16 等へリサンプル）、add_jingles_and_encode（filter_complex で opening / ending を atrim=end=jingle_duration + フェードイン/アウト処理して本編と concat → MP3）
replacement_table.pyTTS 用の読み置換テーブル。英略語や記号など読み誤りしやすい表記を発音用テキスト（spoken_text）へ変換。表示用（display_text）とは分離して script.json に保持

generate_script.py — 台本生成の内部構造

  1. Narrative Arc 生成 — 要約一覧を generate_narrative_arc.md プロンプトに渡し、エピソード全体の共通テーマ・テーマ概要・記事の紹介順序を先に決定。失敗時はアーク無しで続行
  2. 台本生成 — generate_radio_script.md にアーク情報と要約JSONを注入し、lines（speaker / text / article_id / section）を生成。section は intro / news / transition / discussion / outro の5種に正規化
  3. トランジション保証（_ensure_transitions） — article_id の切り替わり境界に transition 行が無ければ、約40種のフレーズプール（news用）と討論導入フレーズ（discussion用）から直前と重複しないよう乱択して挿入。話者は直近3行の偏り（同一話者2連続、男女バランス）を見て自動選択
  4. 自動Linter（lint_script） — 禁止フレーズ、テキスト完全重複、口癖フレーズの2回以上使用、「数字で見ると」と言いつつ数字が無い行、discussion が news より前に出現する構成違反を検出。エラーがあれば前回出力と指摘事項を添えた修正プロンプトで再生成
  5. 採用記事のマーク — 台本に採用した記事を status=used に更新し、翌日以降の重複採用を防止

review_script.py — 4ディレクターレビュー

台本JSONを4種類のキャラクタープロンプト（review_genius_director.md ほか）に通して個別レビューを収集し、review_synthesize.md でフィードバックを統合します。改訂があれば、共有パイプラインは同じエピソードの台本を更新してから最終検証・音声合成へ進みます。レビュー失敗は通常非致命的で、元の台本で後続処理を続けます。

synthesize_voicevox.py — 音声合成の細部

  • WAVファイル名は無音・ジングル挿入分も含む通し番号（001.wav〜）。transition 行の直前にトランジションジングル（24000Hz/mono/s16 へ ffmpeg 正規化してコピー、失敗時は wave モジュールで無音1秒を生成）を挿入
  • 合成成功行には display_text（画面表示用）/ spoken_text（置換適用済み）/ wav_file を書き戻し、script.json を更新
  • エンジン間のレート不一致を防ぐため、最後に lines/ 内のWAVを出力側のサンプリングレートへ正規化（Fish S2 Pro は44100Hz）

build_episode.py — 組み立てとタイムコード

  • lines/ 配下のWAVをソートして結合し、add_jingles_and_encode でオープニング/エンディングジングル（既定10秒・フェード1秒）を付加した episode.mp3 を生成
  • 各セリフ行に start_time（秒）を付与。オープニングジングルの実長（または jingle_duration の小さい方）をオフセットとし、WAV長を累積して算出。wav_file 欠落行（旧エピソード）には file_counter ロジックを再現して推定
  • metadata.json（title / duration_seconds / audio_path / created_at）を出力し、API の一覧・詳細補完に利用

運用・エラー処理

ログ

  • バッチ: logging_config.setup_daily_logging により data/logs/YYYY-MM-DD.log へ集約。cron の標準出力は data/logs/crontab.log に追記され、entrypoint.sh 起動時はDockerログへtailする（現行Compose commandではentrypointを迂回）
  • 日次バッチの最終結果は data/run_manifest.json（done / awaiting_review / failed 等）に保存

障害と復旧

事象挙動・対処
LLM / TTS 停止生成処理が失敗した場合はジョブ・エピソードを失敗として記録。/health/ollama・/health/voicevox で対応エンジンの疎通確認が可能（Fish S2 Proには専用クライアント側の接続確認あり）
記事・台本が不足記事の取得結果や生成可能な要約に応じて処理を終了。日次マニフェストには done / failed などを記録し、skipped_no_new 固定の状態は使用しない
LLM の不正応答プロバイダー別クライアントのパース・検証・再試行と、台本生成時のLint修正で処理。失敗時の継続可否は生成フェーズとLLM設定による
生成ジョブの滞留ジョブはDBの永続キューで管理され、API起動時にキュー復旧処理を実行。要求は Idempotency-Key と stale job 判定により重複・滞留を制御
SQLite ロック競合EpisodeService の書き込みは指数バックオフ付きで最大5回リトライ
ディスク逼迫cleanup_episodes.py が保持期間（既定30日）超過のエピソードを DB・ファイルとも削除（ID ベース／旧日付ベース両ディレクトリに対応）

テスト

  • backend/tests/: 生成フローと stale generating リセットの pytest
  • app/batch/test_ensure_transitions.py / app/services/test_fetch_summaries_for_script.py: トランジション挿入ロジックと台本用要約取得のユニットテスト
